Yep bro, I know exactly the kind of issue you're describing. 😭

If Turnstile **automatically shows the checkmark**, but your login request returns:

> **Security check failed. Please complete the "I am not a robot" verification.**

then the problem is usually **not that Turnstile failed visually**. It's that the **token generated by Turnstile isn't reaching your backend correctly, or the backend isn't accepting/verifying it correctly**.

Your flow should be:

```text
User clicks Login
       ↓
Turnstile widget
       ↓
Turnstile generates TOKEN
       ↓
React receives TOKEN
       ↓
POST /api/auth/login
       ↓
Backend receives token
       ↓
Backend → Cloudflare verification API
       ↓
Cloudflare: success ✅
       ↓
Login continues
```

If you're currently doing:

```text
Turnstile ✅
     ↓
Login
     ↓
Backend
     ↓
"Security check failed" ❌
```

we need to inspect the handoff.

### The 5 things I'd check first

**1. Is the token actually being stored?**

Your Turnstile callback should receive a token and your React state should contain it.

Conceptually:

```js
const [turnstileToken, setTurnstileToken] = useState("");
```

and:

```js
onVerify={(token) => {
  setTurnstileToken(token);
}}
```

Then before submitting:

```js
console.log(turnstileToken);
```

You should see a long token, **not an empty string**.

---

**2. Is the token being sent to Express?**

Your login request needs to include the token.

For example:

```js
body: JSON.stringify({
  email,
  password,
  turnstileToken
})
```

If the frontend calls:

```text
POST /api/auth/login
```

but sends only:

```json
{
  "email": "...",
  "password": "..."
}
```

then the backend has nothing to verify.

---

**3. Does the backend expect the same property name?**

This is a very common bug.

Frontend:

```js
turnstileToken
```

Backend:

```js
req.body.token
```

Those don't match.

Pick one name and use it consistently.

I'd use:

```text
turnstileToken
```

everywhere.

---

**4. Is the backend actually sending the token to Cloudflare?**

Your Express backend needs to verify it server-side.

Conceptually:

```text
POST https://challenges.cloudflare.com/turnstile/v0/siteverify
```

with:

```text
secret
response
```

where:

```text
secret = TURNSTILE_SECRET_KEY
response = user's Turnstile token
```

The **secret must come from Render's environment variables**, not the frontend.

---

**5. Check the actual Cloudflare response**

This is the most useful debugging step.

Don't just return:

```text
Security check failed
```

temporarily log the **verification result on the server**.

Cloudflare returns useful information such as:

```json
{
  "success": false,
  "error-codes": [...]
}
```

The error code will tell us much more than your generic message.

---

### Also check your domain configuration

Because you're now moving Alpha Cut into production, make sure the Turnstile widget's allowed hostname includes the actual hostname you're testing.

For example, if login is at:

```text
https://alpha-cut.com/login
```

the Turnstile configuration needs to allow:

```text
alpha-cut.com
```

If login is at:

```text
https://dashboard.alpha-cut.com/login
```

then that hostname needs to be configured appropriately.

And don't accidentally test a widget configured for:

```text
localhost
```

while running it on:

```text
alpha-cut.com
```

---

### One more thing: don't reuse tokens

Turnstile tokens are **short-lived and single-use**.

So don't:

```text
Get token
   ↓
Store it for 10 minutes
   ↓
Try login again with same token
```

Instead:

```text
Turnstile verified
       ↓
Fresh token
       ↓
Login request
       ↓
Backend verifies
       ↓
Token consumed
```

If login fails and the user tries again, make sure Turnstile gets a **fresh token**.
